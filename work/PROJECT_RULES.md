# 项目开发与操作规则

## 1. 目录管理

项目工作目录：`work`

- `work` 目录用于代码修改、开发、版本跟踪和相关工作。
- 所有正式代码修改均应在该目录中进行。
- 修改过程中应保留必要的项目结构，不得随意删除或重建项目文件。

临时目录：`tmp`

- `tmp` 是临时文件目录，用于存放无用的临时文件、中间文件、临时分析结果等。
- 不要将临时文件混入正式项目代码。
- 任务完成后，可以清理不再需要的临时文件。

工具目录：`E:\AI Games\tools`

- 开发和修复过程中，如果需要额外的工具，可以自行下载安装到该目录。
- 尽量使用独立目录安装工具，不要随意修改系统环境。
- 安装新工具后，记录工具名称、用途及必要的使用方式。

## 2. 模拟器调试

本地已安装 MuMu 模拟器，可以用于 Android 游戏的安装、运行、调试和测试。

- 可以根据实际需要使用 ADB、Logcat 等工具。
- 可以通过模拟器验证修改效果。
- 如果需要额外的调试工具，可以自行安装。
- 优先使用现有环境，避免重复安装已有工具。
- 不得随意清除模拟器游戏数据、存档或重置游戏环境。
- 安装新 APK 时，优先采用覆盖安装，尽可能保留现有数据。

## 3. Git 版本管理规则

Git 用于保存每个独立功能和 Bug 修复的代码版本。

### 3.1 提交原则

- 每完成一个独立的大功能，构建成功后，必须提交 Git 并推送到远程仓库。
- 每完成一个独立 Bug 修复，构建成功后，必须提交 Git 并推送到远程仓库。
- 不同功能之间没有直接关联的，应分别提交，不要合并为一个提交。
- 不要求每次微小代码修改都单独提交。同一功能内部的小幅调整可以合并提交。
- 不要等多个独立功能全部完成后才统一提交。

### 3.2 长期功能的提交

如果一个功能涉及较多代码、开发周期较长，或者需要分多个阶段完成：

- 应提前划分合理的开发阶段。
- 每完成一个具有独立意义的阶段，并且构建成功后，就提交并推送一次 Git。
- 不必等到整个功能完全开发结束才提交。
- 每个阶段的提交都应尽可能保持代码完整、可构建。
- 后续阶段在前一阶段的基础上继续开发。

### 3.3 提交要求

- 每次提交必须使用清晰、具体的提交说明。
- 提交说明应明确指出修改的功能或修复的问题。
- 提交前检查修改文件，避免混入无关内容、临时文件、构建产物或敏感信息。
- 提交完成后必须推送到远程仓库。
- 如果推送失败，应说明原因，不得假装已经上传成功。
- 不得擅自覆盖或删除远程仓库已有的有效提交。

## 4. 功能修改与 Bug 修复流程

每次执行功能开发或 Bug 修复时，按照以下流程进行：

1. 分析现有代码和相关调用关系。
2. 明确问题原因、修改范围和可能影响的功能。
3. 制定修改方案，避免无必要地修改其他模块。
4. 执行代码修改。
5. 完成必要的代码检查和 APK 构建。
6. 构建成功后，根据 Git 规则提交并推送。
7. 生成本次修改对应的 APK。
8. 将新 APK 安装或替换到 MuMu 模拟器中。
9. 整理本次修改内容和需要用户测试的项目。

如果一个功能需要分阶段开发，则每个阶段完成后都按照上述相应流程保存代码版本。

## 5. APK 交付与测试

每次成功完成一个功能或 Bug 修复后，都需要提供可测试的 APK。

具体要求：

- 每次修改成功后，重新构建 APK。
- 将新 APK 安装到 MuMu 模拟器，尽量保留原有游戏数据。
- 向用户说明本次 APK 的生成位置及版本。
- 明确说明本次具体修改了什么。
- 列出需要用户执行的测试操作。
- 明确说明需要重点检查的功能和预期结果。
- 不要只说“已经修复”，必须提供实际可验证的测试内容。

如果无法自动安装或替换 APK，应提供 APK 文件位置和手动安装步骤，并说明遇到的问题。

## 6. 测试反馈与后续修改

- 用户负责实际体验和功能验证。
- 用户反馈测试结果后，根据反馈继续分析和修改。
- 如果测试未通过，应定位原因，不要直接认定功能已经完成。
- 修复后重新构建 APK，并按照 Git 规则保存新的代码版本。
- 每次交付都要明确区分已完成、待测试和未解决的问题。

## 7. 操作说明

每次完成一项功能或 Bug 修复后，都必须向用户列出：

1. 本次修改内容。
2. 修改涉及的主要文件或模块。
3. Git 提交记录及远程推送结果。
4. APK 构建结果和文件位置。
5. 是否已成功替换 MuMu 模拟器中的安装包。
6. 用户需要执行的测试步骤。
7. 预期测试结果。
8. 当前仍存在的问题或需要注意的事项。

所有操作说明应具体、清晰，让用户能够直接按照步骤进行测试。

## 8. 测试交付后的停止规则（重要）

本项目采用「开发完成 → APK 交付 → 用户测试 → 根据反馈继续开发」的工作模式。

### 8.1 交付后必须停止

每次完成代码修改、构建 APK、Git 保存以及模拟器安装后，必须整理本次修改内容和测试说明，然后结束当前任务。

用户收到 APK 后，由用户负责实际测试。必须等待用户测试完成并反馈结果，才能继续下一步工作。

### 8.2 禁止交付后继续操作

APK 交付后，未经用户明确授权，不得：

- 继续操纵 MuMu 模拟器。
- 继续启动、关闭或重启游戏。
- 持续监控或实时查看 Logcat。
- 持续观察模拟器运行状态。
- 根据实时日志自行修改代码。
- 擅自重新构建或替换 APK。
- 在后台继续执行当前修复任务。

### 8.3 允许的交付前检查

在正式交付之前，可以进行必要的自动化检查，例如：

- 检查 APK 是否成功构建。
- 检查 APK 是否能够正常安装。
- 检查游戏是否能够正常启动。
- 检查是否存在明显的启动崩溃。
- 查看必要的启动日志。

这些检查仅用于确认 APK 具备交付条件，不代表已经完成用户实际测试。

### 8.4 后续工作必须等待用户指令

交付后进入等待状态。

只有在用户提供测试结果、反馈 Bug 或明确要求继续操作时，才能恢复开发工作。

如果用户反馈测试通过，则记录该功能已经通过测试。

如果用户反馈测试失败，则根据反馈重新分析、修改、构建、保存 Git 并交付新的 APK。

不得将自动化检查等同于用户测试，也不得在用户尚未反馈时自行开启下一轮修改。

### 8.5 最终交付标志

每次交付结束时，必须明确告知：

- 本次开发任务已完成。
- APK 已交付。
- 用户需要测试的内容。
- 当前等待用户测试反馈。

告知上述内容后立即停止操作，不再继续执行其他开发、调试或监控任务。
